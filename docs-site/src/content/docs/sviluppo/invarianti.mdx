Le **invarianti** sono le proprietà che devono valere **sempre**. Ognuna ha un numero stabile e il test che la
verifica; l'elenco completo, con stato e nome dei test, è in `docs/invariants.md`. Un cambiamento che tocca
disponibilità, prezzi, prenotazioni o pagamenti deve lasciarle tutte valide (in Claude Code lo controlla il
subagent `invariants-guardian`).

| # | Invariante |
|---|---|
| INV-01 | Nessuna doppia allocazione di una postazione, anche con 100 richieste parallele, su SQLite e PostgreSQL |
| INV-02 | Il pool non supera la capacità effettiva |
| INV-03 | `pool_usage` coincide con il dettaglio delle allocazioni |
| INV-04 | Una postazione è occupata se e solo se esiste un'allocazione valida |
| INV-05 | Gli hold scaduti non bloccano mai le vendite |

## Come si verificano

- **Unit**, table-driven, `TestXxx_Scenario`; **di proprietà** con `pgregory.net/rapid` per prezzi e disponibilità.
- **Integrazione** con build tag `integration`: SQLite in memoria sempre, PostgreSQL quando è impostata
  `ARENILE_TEST_POSTGRES_URL` (`make test-db` avvia il container).
- **Concorrenza**: test `TestConcurrency_*` con `-race` e almeno 100 tentativi paralleli sulla stessa risorsa
  (`make test-race`), incluso quello tra cassa e online sulla stessa postazione.
- **Accettazione**: `internal/acceptance` avvia l'applicazione reale con un orologio finto, la usa solo dalle API
  (centinaia di operazioni, raffiche concorrenti) e controlla le invarianti sul database, su entrambi i dialetti.

<Aside type="note">
  Una nuova invariante si aggiunge in coda con il numero successivo, insieme al suo test; i numeri non si
  riusano.
</Aside>
